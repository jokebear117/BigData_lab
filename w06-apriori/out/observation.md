# Week 6 observation.md

## Task 1

`diaper`와 `cola`는 2개 장바구니에서 함께 나왔다. 따라서 `diaper → cola` 신뢰도는 2/5=0.4, 반대 방향 `cola → diaper`는 2/2=1.0으로 비대칭이다. 다만 이 쌍은 support 3 기준의 빈발쌍에는 들지 않는다.

가장 높은 빈발 규칙 중 하나는 `diaper → beer`로 confidence 0.8, lift 1.12다. 맥주가 전체 장바구니의 5/7에 들어 있어 lift가 1에 가까우므로 강한 연관이라고 보기는 어렵다.

항목 2,000개를 무차별 비교하면 쌍 카운터는 2,000×1,999/2 = 1,999,000개다. 이 데이터에서 support 50을 통과한 단일 항목은 1,849개이고, 가능한 조합은 1,708,476개다. 실제 바구니에 등장해 A-Priori가 보관한 peak 카운터는 820,259개였다.

## Task 2

support 1까지 측정했으며 peak traced memory는 327.1 MB, 처리시간은 7.05초였다. 16 GB 메모리가 고갈되지는 않았고, 생성 데이터에서 나타난 서로 다른 쌍 893,456개가 카운터 상한을 만들었다.

support를 절반으로 낮출 때 카운터는 support 400→200에서 5.54배, 200→100에서 4.67배, 100→50에서 3배 증가한 뒤 893,456개에서 포화됐다. 답 쌍은 support 50의 6,397개에서 support 1의 893,456개로 늘어, 낮은 임계값이 계산량을 크게 키우는 이유를 보여준다.

## Task 3

PCY는 100,003개 버킷을 사용했다. 버킷 수를 소수로 두고 고정 크기의 카운트 배열을 pass one에 쓴 뒤, 이를 비트맵으로 바꿔 pass two에서 희소한 버킷을 거른다. Python 3.12에서 이 배열은 입력이 100 basket일 때도 traced peak 약 0.95 MB를 차지했고, 이후 pass two의 비트맵은 약 0.1 MB다.

peak pair counters는 820,259개에서 148,595개로 81.9% 줄었고 결과는 동일했다. 대신 pass one에는 약 100,003개 카운터 배열(대략 4 MB)과 이후 약 0.1 MB 비트맵이 필요하다. 버킷을 1,000개로 줄이면 충돌로 거의 모든 버킷이 살아남아 820,259개 카운터로 되돌아왔다.

입력 크기별 traced peak memory를 비교하면 2,000 basket에서 baseline 0.79 MB, PCY 1.05 MB로 baseline이 작았고, 5,000 basket에서는 각각 6.42 MB와 1.16 MB로 역전됐다. 이 실행에서는 crossover가 대략 3,000 basket 부근이다. 이는 고정 버킷 비용과 pair 분포에 따라 달라지며, 20,000 basket에서는 baseline 102.41 MB, PCY 15.63 MB였다.

## Task 4 · optional SON

전역 빈발쌍이 모든 청크에서 비빈발이라고 가정하면, 각 청크의 지지도는 전체 지지도의 합보다 작아 전역 지지도에도 못 미친다. 그런데 모든 청크에서 비빈발이면 각 청크 count < `support × chunk_size / total_size`다. 이를 합하면 전체 count < support가 되어 전역 빈발이라는 가정과 모순이다. 그러므로 적어도 한 청크에서 후보로 발견된다.

청크 수를 4, 8, 16으로 바꾸자 후보 수는 9,876 → 14,201 → 24,418로 변했지만, 검증된 정답 6,397개는 변하지 않았고 false negative도 없었다. Spark 실행은 후보 14,695개, 정답 6,397개, missing 0으로 12.46초 걸렸다. 단일 프로세스는 8청크에서 2.21초였다.

여기서는 데이터가 한 머신에 들어가고 Spark 시작·분산 비용이 커서 SON이 유리하지 않았다. 그래도 데이터가 한 머신 메모리를 넘으면 청크별 pass one으로 후보를 모으고 전체 pass two로 검증하는 SON이 맞는 선택이다.
